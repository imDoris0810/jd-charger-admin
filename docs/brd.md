# 业务需求文档（BRD）

> 项目：京东充电桩安装协同管理后台
> 使用方：京东业务侧四角色（内网）+ 服务商侧两角色（公网账号）
> 上位依据：《需求基线》（`docs/requirements-baseline.md`）
> 编号规则：本文使用 **R-xx** 条目编号；**F-xx** 保留给 PRD 阶段的功能点，两套编号不混用

## 1. 业务背景

当前同一笔充电桩安装业务的信息，分散在四个互不相通的系统中；各服务商的记录方式、字段口径和资料模板也各不相同：

- **城南安装**：本地用领退料方式记录，没有独立的「桥架安装」项
- **远程机电**：按分段工程记录，桥架材料与安装拆成两条
- **安家安装**：用 Excel 交付，字段名、单位与京东标准不一致

这些记录方式本身没有对错。问题在于：它们与京东标准字段、项目和办理位置之间**没有稳定的对应关系**，于是每一次交付都要**人工解释、改表、复制和重复录入**，而且交接过程**无留存**。

由此产生的具体问题：

- 同一安装工单的信息散落在服务商本地系统、京东订单系统、京东安装履约系统、京东安装管理系统和京东账单模块中，查询需要跨系统；
- 资料在两侧流转时，来源、配置版本、提交版本和确认人无法追溯；
- 原方案、现场变化、实际完工记录和正式核查结果容易混淆；
- 服务商本地应收与京东正式账单的拆分方式不同，人工对账成本高；
- 自动交接或新入口异常时，容易重复提交或丢失当前办理位置；
- 已在一侧确认过的事实，进入另一侧还要再填一遍。

> 本次要做的**不是替换**服务商本地系统、京东安装履约系统、京东安装管理系统或京东账单系统。新增的是一个围绕**同一安装工单**的协同管理后台：**原系统继续负责正式业务**，新后台只负责聚合、交接、辅助、对照和追溯。

## 2. 典型案例

> **案例一：拆分方式不同，金额其实一致**
> - 服务商本地应收：桥架材料 **216 元** ＋ 桥架安装 **144 元** ＝ **360 元**
> - 京东正式账单：桥架综合 **360 元**
>
> 人工比对是两个项目对不上；按含义建立对应后，结论是「拆分方式不同，金额一致」，不需要人工解释。

> **案例二：无对应项，形成待核差异**
> - 服务商：额外搬运 **60 元**
> - 京东：无独立对应项
>
> 系统计算出的不是「服务商多报」，而是 **60 元待核差异**：需调取合同范围和批准材料后才能处理。系统不下责任结论、不改任何一方账目、不扣款、不付款。

> **案例三：同一类资料，三种交付方式**
> - 城南安装：在本地系统确认后自动交接
> - 远程机电：上传文件并确认交付
> - 安家安装：直接在京东入口填写/导入
>
> 三条路径**共用同一套**京东原校验与提交能力，正式结果各自返回原办理位置（本地任务 / 文件交付事项 / 当前京东工单），且不因接入新后台而多出任何审批。

> **案例四：依据不足时，AI 不编造**
> - 附件中只有一句「已加长线缆」，未给出长度，照片中也没有可参照的标尺
>
> 结构化 Prompt 输出的是「**证据不足**」和待确认问题清单，转人工向服务商补充；**不生成数量、不推进提交、不形成结论**。

## 3. 功能范围（In Scope）

### 3.1 功能模块

| 编号 | 需求标题 | 一句话说明 |
| --- | --- | --- |
| R-01 | 工单中心 | 按京东工单聚合订单范围、本地任务关联、责任岗位、方案与实际完工、资料来源和三类状态；多次上门不自动新开京东工单 |
| R-02 | 统一工单详情 | 以六个页签承载全量信息，并强制显示数据来源系统、原始与正式记录、配置版本、办理位置、AI 草稿标识和正式核查结果 |
| R-03 | 服务商接入配置 | 按「服务商 × 来源系统 × 记录/资料类型 × 模板版本」维护版本化配置，含字段对应、项目拆分合并与计算规则、单位和提交返回位置 |
| R-04 | 三种资料入口与结果返回 | 支持本地系统自动交接、文件交付、直接使用京东入口三条路径，共用同一套正式校验与提交能力 |
| R-05 | 资料整理 | 结构化字段由普通程序处理，仅非结构化说明与附件使用结构化 Prompt，保留来源位置与草稿/人工/正式版本区分 |
| R-06 | 核查、补充与复核 | 承载六类核查状态，同屏展示原方案、完工明细、确认变更、附件来源、问题与补充内容；证据不足只能退回补充 |
| R-07 | 方案与变更事实追溯 | 只关联原方案版本、现场变化、变更原因、影响字段和批准材料，不新建变更审批流 |
| R-08 | 业务对账 | 在双方账目不互相覆盖的前提下建立项目对应、合并计算、算出差额；Prompt 只解释差异，不认定责任、不改金额 |
| R-09 | 档案、施工比较与查询 | 留存原文件、配置版本、草稿与正式版本、问题回复和差异处理历史，支持跨服务商比较 |
| R-10 | 三类业务状态独立 | 现场履约、资料交接、对账处理各自流转，不合并为单一总状态 |
| R-11 | 记录分层与原始数据不可覆盖 | 原始记录 → 转换结果 → AI草稿 → 人工确认稿 → 正式版本 → 原系统结论，后一层不得覆盖前一层 |
| R-12 | 普通程序与 AI 的分工边界 | 确定性转换、校验、计算、提交、幂等由程序负责；Prompt 只出草稿，无依据必须「证据不足」 |
| R-13 | 幂等、防重复与异常续办 | 以「京东工单号＋资料类型＋提交版本」为唯一键，重复交付不产生重复正式结果，异常从最近确认节点续办 |
| R-14 | 分批启用与历史事项迁移 | 按服务商、资料类型、办理事项、模板版本、项目/合同范围和批次逐步启用 |
| R-15 | 角色权限与访问方式 | 六类角色职责与禁止行为固定；京东内部四角色仅内网，服务商侧两角色公网账号鉴权 |

> **业务规则（R-03）**：接入配置**必须经双方确认才能生效**——**服务商确认本地含义** ＋ **京东业务确认接收要求**，双方都确认后由审核人审核生效。接入配置管理员只能维护草稿和适用范围，**不得单方面让配置生效**。
>
> 配置按「一类记录/资料模板」建立，不是整家服务商永久不变的通用规则。生效后的新版本只对**此后**的工单复用，**不得覆盖**已使用旧版本的历史工单。数量、工人、供应商或现场情况的变化属于工单事实，不产生新配置版本；模板、字段含义或项目划分变化才建立新版本。

### 3.2 接入配置示例

同一笔桥架费用（见案例一），两家服务商的本地字段名完全不同，映射到的是**同一个京东标准项**：

| 京东标准项 | 城南安装 | 远程机电 |
| --- | --- | --- |
| 桥架综合施工<br>（含材料、配件、安装） | 来源：领退料记录<br>本地字段：`桥架材料` ＋ `桥架安装`<br>处理：两条合并为一项 | 来源：分段工程记录<br>本地字段：`桥架·材料` ＋ `桥架·安装`<br>处理：两条合并为一项 |

> 映射关系只需确认一次。保存为生效配置后，同类新工单直接复用，不再需要人工解释「216 ＋ 144 为什么等于 360」。
>
> 上表只列出映射相关字段，实际配置还包含适用范围、生效周期、提交与返回位置等（见 R-03）。

## 4. 功能范围（Out of Scope）

- 不替换服务商本地系统、京东安装履约系统、京东安装管理系统和京东账单系统
- 不重新建设勘测、排班、施工、库存、领退料、验收和客户交付
- 现场工人端与移动端（施工人员继续使用服务商本地系统）
- 照片直传、施工进度填报
- 不新建施工验收状态机
- 不新建变更审批流
- 京东正式账单的生成、调整、结算和付款
- 自动责任认定
- 覆盖服务商本地成本、工资、其他客户和经营数据
- 独立 Skill、复杂 Agent、RAG 和向量数据库
- 完整 BI 看板
- MVP 期不接所有真实外部系统接口（由**清晰标注**的数据适配层和模拟数据代替，**不伪装成已接通真实生产系统**）

## 5. 成功标准

### 5.1 必须达成

- 在一个工单详情中即可区分并查看多系统来源的信息
- 现场履约、资料交接、对账处理三类状态独立可见
- 接入配置可创建、经双方确认后生效，并能被同类新工单复用一次以上
- 三种资料入口均可演示，且结果返回正确位置
- 相同结构化输入由普通程序稳定产生相同转换结果
- AI 输出明确标注为草稿，并附来源依据与待人工确认问题；缺依据时不补造，可转人工
- 正式提交前必须经过人员确认和原系统校验
- 两边账目可完成项目对应、合并与差额计算，且不修改任何一方原账
- 重复提交不产生重复正式记录
- 自动能力异常时可从原办理位置继续
- 原始记录、配置版本、草稿、正式版本、问题和处理人全程可追溯

### 5.2 量化指标

| 指标 | 现状 | 目标 |
| --- | --- | --- |
| 单笔工单资料交接的人工改表/重复录入耗时 | 约 25 分钟 | 约 6 分钟 |
| 单笔对账差异的解释与查证耗时 | 30 分钟 | 5 分钟 |
| 同类记录第二次交接所需的配置工作量 | 每次重新解释 | 趋近于 0（复用生效配置） |
| 同一事实的重复录入次数 | — | 0 |
| 正式结果可追溯覆盖率 | 无留存 | 100% |

> 上表耗时数据为**估算值，非实测**。本项目不上线运行，不要求真实运行数据。
