# 京东充电桩安装协同管理后台｜最终需求基线

> 文档状态：最终确认基线  
> 依据：第二课业务流程与系统设计、`jd-charger-admin 1.0` 审计、历次产品边界讨论  
> 使用方式：后续 `AGENTS.md`、BRD、交互原型、数据库设计、主子 PRD、开发计划和测试用例均以本文为上位依据。

## 1. 一句话定位

在不替换服务商本地系统、京东安装履约系统、京东安装管理系统及京东账单系统的前提下，新增一个围绕同一安装工单的协同管理后台，通过可配置的资料交接、确定性字段转换、辅助核查、双账对比和全程追溯，减少人工改表、重复录入、跨系统查找及差异解释成本。

## 2. 产品本质

本产品是连接“服务商本地系统”和“京东原业务系统”的协同中间层，不是新的完整安装履约系统。

平台负责：

- 聚合同一安装工单在不同系统中的关联信息；
- 配置服务商本地记录与京东标准字段、项目和办理位置的对应关系；
- 支持本地自动交接、文件交付、直接使用京东入口三种资料路径；
- 使用普通程序完成确定性转换、校验、计算、提交和结果返回；
- 使用结构化 Prompt 生成字段映射建议、资料整理草稿、核查提示和差异解释；
- 保留原始记录、配置版本、草稿、正式版本、问题、回复和处理历史；
- 对服务商本地应收与京东正式账单进行独立对照；
- 在系统或自动能力异常时，从原办理位置继续处理。

平台不负责：

- 重新建设勘测、排班、施工、库存、领退料、验收和客户交付系统；
- 重新建设京东正式账单或付款系统；
- 覆盖服务商本地成本、工资、其他客户和经营数据；
- 代替原岗位完成专业判断、审批、正式核查或责任认定；
- 自动修改服务商应收、京东账单或执行付款；
- 开发独立 Skill、复杂 Agent、RAG 或向量数据库。

## 3. 核心业务目标

### 3.1 当前问题

- 服务商本地记录方式、字段口径和资料模板不一致；
- 同类资料需要人工解释、改表、复制和重复录入；
- 资料在服务商本地、京东服务商端和京东管理后台之间流转时难以追溯；
- 原方案、现场变化、实际完工记录和正式核查结果容易混淆；
- 服务商本地应收与京东正式账单拆分方式不同，人工对账成本高；
- 自动交接或新入口异常时，容易重复提交或丢失当前办理位置。

### 3.2 目标状态

- 同一工单的信息、资料、核查、对账和历史可以在一个工单详情中查询；
- 同类服务商记录完成一次映射确认后可复用；
- 同一事实只确认一次，不因进入新系统重复填写；
- 确定性规则由程序稳定执行，需要理解的内容由结构化 Prompt 辅助；
- 所有正式结果仍由原业务系统和原岗位产生；
- 双方账目保持独立，只建立对应、计算差额和保留处理依据；
- 异常恢复后只续办未完成部分，不重做整笔工单。

## 4. 最高业务原则

1. **原系统继续负责正式业务。** 新后台只聚合、交接、辅助、对照和追溯。
2. **原始数据不得覆盖。** 原始记录、转换结果、AI草稿、人工修改和正式结果分层保存。
3. **同一事实只确认一次。** 已在原责任位置确认且成功交接的内容不得要求重复录入。
4. **不同事实由不同系统负责。** 不设置笼统的“唯一真相系统”，按字段和记录类型确定权威来源。
5. **三类状态独立。** 现场履约、资料交接、业务对账不能合并成一个总状态。
6. **双账独立。** 服务商本地应收和京东正式账单互不覆盖、互不复制生成。
7. **AI只提供草稿。** 无依据时必须输出“证据不足”，不得编造事实或自动下正式结论。
8. **正式结果可追溯。** 必须知道来源、配置版本、提交版本、确认人、办理位置和历史变化。
9. **异常可以续办。** 新入口或自动能力不可用时，原入口和原业务能力仍可继续使用。
10. **分批迁移。** 按服务商、资料类型、办理事项和模板版本逐步启用。

## 5. 系统边界与记录归属

| 系统/位置 | 继续负责的内容 | 新后台的关系 |
| --- | --- | --- |
| 服务商本地系统 | 本地任务、人员安排、勘测、施工、完工、材料领退、库存、本地应收 | 读取经服务商确认且在接入范围内的记录；返回交接结果和问题 |
| 京东订单系统 | 购买范围、安装服务和工单来源 | 读取订单与服务范围，建立工单关系 |
| 京东安装履约系统 | 接单、预约、派工、条件、方案、变更、施工、验收和用户确认 | 引用正式方案、变更、履约和验收结果；不重建流程 |
| 京东安装管理系统 | 正式资料接收、校验、补充、复核、历史和正式核查结论 | 调用原校验/提交能力，读取正式版本及结果 |
| 京东账单模块 | 京东正式账单、调整和结算结果 | 只读正式账单并用于对账，不修改、不付款 |
| 新协同后台 | 接入配置、交接过程、草稿、问题、回复、对应关系、差异和追溯 | 保存新增的过程记录，不冒充原系统正式记录 |

## 6. 用户角色与权限

| 角色 | 主要职责 | 不允许的行为 |
| --- | --- | --- |
| 服务商资料负责人 | 确认本地交接范围、上传文件、提交资料、查看退回问题、补充材料 | 不得确认京东正式核查结论 |
| 服务商业务负责人 | 确认本地应收、查看差异、提供合同或批准依据、反馈处理意见 | 不得修改京东账单 |
| 京东资料核查人员 | 查看正式资料、提出问题、复核补充、形成原系统正式结论 | 不得替服务商修改本地事实 |
| 京东业务对账人员 | 建立或确认账目对应、查看差额、记录处理意见 | 不得直接改账或执行付款 |
| 接入配置管理员 | 维护接入配置草稿、适用范围和版本 | 不得单方面让配置生效 |
| 系统管理员 | 用户、角色、权限和基础维护 | 不得代替业务岗位作专业结论 |

现场施工人员继续使用服务商本地系统，MVP不建设现场工人端、移动端、照片直传、排班或施工进度填报能力。

## 7. 核心功能模块

### 7.1 工单中心

按京东工单查询和筛选，同一安装任务聚合：

- 京东订单及安装服务范围；
- 京东安装工单与服务商本地任务的关联；
- 当前服务商、项目和责任岗位；
- 原方案、有效变更和实际完工结果；
- 资料来源、交接方式和当前办理位置；
- 现场履约、资料交接、对账三类独立状态；
- 待办、异常和最近更新时间。

同一安装任务可以存在多次上门、多份资料和多个历史版本，但不能因此自动生成新的京东工单。

### 7.2 统一工单详情

建议包含以下页签：

1. 工单概览；
2. 条件、方案与变更事实；
3. 安装资料与交接；
4. 核查、补充与复核；
5. 业务对账；
6. 档案、施工比较与历史。

页面必须明确显示：

- 数据来源系统；
- 原始记录与当前正式记录；
- 当前使用的配置和版本；
- 当前办理位置和责任人；
- AI生成内容的草稿标识；
- 正式提交版本和正式核查结果；
- 问题、回复和处理依据。

### 7.3 服务商接入配置

配置对象是一类服务商记录或资料模板，不是整家服务商永久不变的通用规则。

配置内容包括：

- 服务商；
- 来源系统；
- 记录类型/资料类型；
- 模板名称和模板版本；
- 本地任务与京东工单的关联方式；
- 本地字段与京东标准字段对应；
- 项目拆分、合并及计算规则；
- 单位转换规则；
- 供料方、施工方和服务范围的表达方式；
- 正式提交的京东原办理位置；
- 结果返回位置；
- 适用项目、合同、服务范围和批次；
- 生效时间、失效时间；
- 创建人、双方确认人和审核人；
- 草稿、待确认、生效、停用状态。

配置生命周期：

```text
AI生成映射建议 → 服务商确认本地含义 → 京东业务确认接收要求
→ 保存配置草稿 → 审核生效 → 同类新工单复用
```

配置变更规则：

- 数量或具体事实变化：继续使用原配置，读取本单实际值；
- 适用合同变化：按有效合同判断，存在争议时转人工；
- 新模板、字段含义或项目划分变化：建立新配置版本；
- 新版本不得覆盖已使用旧版本的历史工单；
- 工人、供应商或现场情况变化属于工单事实，不属于接入配置版本。

### 7.4 三种资料入口与结果返回

#### A. 本地系统自动交接

```text
服务商在本地确认 → 新后台读取授权内容 → 按生效配置转换和校验
→ 调用京东原校验/提交能力 → 正式结果返回本地任务
```

#### B. 文件交付

```text
服务商上传本次文件并确认交付 → 新后台转换和校验
→ 人工确认后正式提交 → 结果返回文件交付事项
```

#### C. 直接使用京东入口

```text
服务商在京东入口填写/导入 → 调用原标准校验和提交能力
→ 结果返回当前京东工单
```

三种路径使用同一套正式校验和提交能力；没有原核查要求的资料不得因为接入新后台而新增审批。

### 7.5 资料整理

结构化字段由普通程序直接处理；只有需要阅读的非结构化说明、图片描述和附件才使用结构化 Prompt。

整理结果必须包含：

- 原始内容；
- 提取的项目、数量、单位、供料方和服务范围；
- 每项内容的来源位置；
- 缺失事实和待确认问题；
- AI草稿、人工修改和正式版本的区分。

资料整理不得：

- 用套餐长度替代实际完工长度；
- 将材料和安装数量错误相加；
- 根据其他工单推断本单供料方；
- 填写输入中没有的施工事实。

### 7.6 核查、补充与复核

本模块是资料核查协同，不是重新建设施工验收系统。

核查状态：

- 自动校验通过；
- 待人工确认；
- 证据不足；
- 待服务商补充；
- 已退回修改；
- 正式核查通过。

平台需要同时展示：

- 原方案及有效确认材料；
- 实际完工明细；
- 已确认的变更事实；
- 相关附件和来源位置；
- 原岗位提出的问题；
- 服务商补充内容；
- 正式核查结论。

缺少事实或授权依据时，只能退回原责任人补充，不能生成“已确认”的证明。

### 7.7 方案与变更事实追溯

新后台不建立新的变更审批流，只关联：

- 原方案和方案版本；
- 现场实际变化；
- 变更原因；
- 影响字段；
- 有效批准或确认材料；
- 是否影响资料交接；
- 是否影响费用对账。

变更是否有效仍由原业务系统和原岗位判断。

### 7.8 业务对账

服务商本地应收和京东账单保持独立。

普通程序负责：

- 确认同一工单、承担方和服务范围；
- 建立或读取双方项目对应关系；
- 对相同含义项目进行合并计算；
- 分别计算双方合计；
- 计算差额；
- 保留双方原始项目、金额和版本。

例如：

```text
服务商：桥架材料216元＋桥架安装144元＝360元
京东：桥架综合360元
结论：拆分方式不同，金额一致

服务商：额外搬运60元
京东：无独立对应项
结论：形成60元待核差异，需查看合同范围和批准材料
```

结构化 Prompt 只负责根据已提供的合同、说明和批准材料解释差异，不能认定责任、修改金额、扣款或付款。

### 7.9 档案、施工比较与查询

支持按工单查看：

- 原文件和原记录人；
- 原始附件位置；
- 配置版本；
- AI草稿和人工修改；
- 正式提交版本；
- 问题、回复和正式核查结论；
- 本地应收、京东账单和差异处理历史；
- 不同服务商工单的工程量、供料方和服务范围比较。

未提交草稿和未解决问题必须与正式结果分开显示。

## 8. 状态模型

### 8.1 三个独立业务状态

| 状态维度 | 建议状态 |
| --- | --- |
| 现场履约状态 | 待履约 / 履约中 / 待整改 / 已完工 / 已验收 |
| 资料交接状态 | 未交接 / 转换中 / 待确认 / 提交中 / 待补充 / 已完成 / 异常 |
| 对账处理状态 | 未开始 / 待对账 / 有差异 / 处理中 / 已确认 |

“资料已收到”不等于“正式提交成功”；“正式提交成功”不等于“核查通过”；“对账已确认”不等于“已经付款”。

### 8.2 记录层级

```text
原始记录 → 转换结果 → AI草稿 → 人工确认稿 → 正式提交版本 → 原系统正式结论
```

后一个层级不能覆盖前一个层级。

## 9. 普通程序与结构化 Prompt 的分工

### 9.1 普通程序必须负责

- 配置读取和版本判断；
- 字段转换和单位换算；
- 项目合并和金额计算；
- 必填、格式、范围和重复校验；
- 工单、资料和账目的关联；
- 正式提交和结果返回；
- 状态流转；
- 幂等、防重复和重试；
- 权限和操作日志。

### 9.2 结构化 Prompt 只负责

1. 字段映射建议；
2. 非结构化资料整理；
3. 核查问题辅助；
4. 对账差异解释。

所有 Prompt 必须遵守：

- 只使用提供的工单内容、有效配置、合同、批准材料和历史记录；
- 每项结论标明依据来源；
- 不知道时输出“证据不足”；
- 不得补造现场事实；
- 不得自行发布配置；
- 不得形成正式核查结论；
- 不得修改账目、扣款、付款或生成付款指令；
- 输出始终为 `draft`，由人员确认后才能进入下一步。

### 9.3 推荐技术实现

不开发独立 Skill。使用一个通用AI辅助接口和四个 Prompt 模板：

```text
POST /api/ai/assist

scenario:
- mapping_suggestion
- material_organizing
- verification_assistance
- reconciliation_explanation
```

Prompt 输出采用固定 JSON Schema，至少包含：摘要、建议、依据、缺失证据、待人工确认问题、置信度和草稿状态。

## 10. 权威来源和冲突处理

不同字段分别指定权威来源：

| 内容 | 权威来源 |
| --- | --- |
| 购买范围和安装服务 | 京东订单系统 |
| 正式方案、变更和履约结论 | 京东安装履约系统 |
| 现场实际数量和本地施工记录 | 服务商本地系统中经责任人确认的记录 |
| 正式资料及核查结论 | 京东安装管理系统 |
| 服务商应收 | 服务商本地应收记录 |
| 京东正式账单 | 京东账单模块 |
| 新增交接过程、草稿、映射和差异 | 新协同后台 |

出现不一致时，不自动选择一方覆盖另一方；平台展示差异、依据和责任岗位，由原责任岗位处理。

## 11. 幂等、防重复与异常续办

建议使用以下业务唯一键：

```text
京东工单号＋资料类型＋提交版本
```

异常规则：

| 异常 | 处理方式 |
| --- | --- |
| AI不可用 | 保留原始内容，允许人员手工整理和判断 |
| 自动交接无明确结果 | 先查询原系统是否已有正式版本，未交付后再重试 |
| 新服务商端或新管理后台不可用 | 回到原入口续办，保留当前版本、问题和责任人 |
| 原业务系统不可用 | 保留待办和资料，恢复后继续；不得把未保存内容标成已完成 |
| 新模板无法匹配配置 | 暂停该资料类型的自动处理，进入配置修订；其他工单继续 |
| 提交中断 | 从最近一次确认节点续办，不重新生成整笔正式记录 |

重复交付不得产生重复正式结果；较早配置版本不得覆盖后来已确认记录。

## 12. 分批启用和迁移

启用维度：

- 服务商；
- 资料类型；
- 办理事项；
- 模板版本；
- 项目/合同范围；
- 生效批次。

历史事项保持原入口查询，不重新调用AI、不要求服务商重交；处理中事项默认按原方式完成，切换时从当前办理位置继续。

## 13. MVP页面与范围

### 13.1 MVP主页面

1. 工单列表；
2. 统一工单详情；
3. 服务商接入配置；
4. 资料交接/异常待办；
5. 业务对账。

资料核查、方案与变更、档案历史优先作为工单详情页签，不在第一版拆成大量独立页面。

### 13.2 MVP必须跑通的链路

```text
建立接入配置并审核生效
→ 从本地记录、文件或京东入口取得资料
→ 普通程序转换与校验
→ AI整理非结构化内容（可选）
→ 人工确认
→ 调用原系统正式提交
→ 返回结果或退回问题
→ 补充与复核
→ 读取两边独立账目
→ 程序对应项目并计算差额
→ AI生成差异解释草稿（可选）
→ 责任人处理
→ 保存完整追溯记录
```

### 13.3 MVP暂不实现

- 现场工人端和移动端；
- 人员排班、勘测、施工进度、库存、领退料；
- 新的施工验收状态机；
- 新的变更审批流；
- 京东正式账单生成、调整、结算和付款；
- 自动责任认定；
- 独立Skill、Agent、RAG和向量数据库；
- 完整BI看板；
- 所有真实外部系统接口。

真实接口在MVP中可由清晰标注的数据适配层和模拟数据代替，但不得伪装成已经接通真实生产系统。

## 15. 验收标准

MVP至少满足：

1. 能在一个工单详情中区分并查看多系统来源；
2. 能独立显示现场履约、资料交接和对账状态；
3. 能创建、确认、生效和复用一个接入配置版本；
4. 能演示三种资料入口及结果返回位置；
5. 相同结构化输入由普通程序稳定产生相同转换结果；
6. AI输出明确标为草稿并附带来源和待确认问题；
7. 缺少事实时AI不会补造结果，系统可转人工；
8. 正式提交前必须经过人员确认和原系统校验；
9. 能对两边独立账目进行项目对应、合并和差额计算；
10. 对账不会修改任何一方原账；
11. 重复提交不会生成重复正式记录；
12. 自动能力异常时能够从原办理位置继续；
13. 能追溯原始记录、配置版本、草稿、正式版本、问题和处理人。

## 17. 最终产品表述

京东充电桩安装协同管理后台连接服务商本地系统与京东原业务系统，在保持双方原流程、正式记录和岗位权限不变的前提下，通过版本化接入配置、三种资料交接路径、确定性字段转换、结构化Prompt辅助核查、双账独立对比以及异常续办与全程追溯，降低资料交接和对账中的人工改表、重复录入与跨系统查找成本。
